# 支付与争议解决原语一致性审计需求摘要 v2

## 目标

在已完成 Pay、Resolve Schema 拆分迁移的基础上，整体审计并修正支付原语、争议解决原语、共享 Action/HAI Schema 与对应规范文档之间的逻辑不自洽，确保状态、结果、金额、责任、补偿和示例能够形成可验证的闭环。

## 使用方

- UTP 原语实现方与 PaymentProcessor、Arbiter 等能力提供方。
- 生成 SDK、校验器、编排器和测试数据的协议工具链。
- 阅读 Pay、Resolve 规范并据此接入的 Agent 与开发者。

## 功能点

1. 审计 50 个已迁移或受影响 Schema 的 JSON 语法、Draft 2020-12 合法性、相对 `$ref`、字段描述和命名。
2. 审计 Pay 的 Action 输入输出、PaymentEvent、状态机、分阶段付款、退款、结算与金额约束是否一致。
3. 审计 Resolve 的争议范围、锁定策略、调解/仲裁结果、责任分配、ResolutionOutcome、补偿执行与状态机是否一致。
4. 审计统一 Action 信封与 HAI 请求/响应方向、幂等和 V2 权威数据源约束。
5. 修正规范文档中与 Schema 不一致的信封层级、字段名、枚举、金额表示和示例对象结构。
6. 增加实例级正反例验证，覆盖关键条件分支，而不只验证元 Schema。

## 边界与异常

- 异步支付或退款处于 `processing` 时不得伪造成功确认或完成事件，也不得提前进入补偿完成状态。
- 失败、驳回、继续履行、升级和无和解等结果不得携带与其语义冲突的完成凭证或补偿指令。
- 支付、退款、赔偿和锁定金额不得为负；需要实际资金动作的金额必须大于零。跨字段金额守恒与币种一致性由 Schema 描述和运行时约束共同保证。
- 条件 Schema 必须同时提供正例和反例，避免 `if` 在字段缺失时意外命中。
- 收紧约束时优先拒绝此前本就没有合法业务语义的数据；不改动与 Pay/Resolve 无关的原语。

## 不做的事

- 不实现 PaymentProcessor、Arbiter、支付渠道或全局状态机的运行时代码。
- 不新增支付方式、争议类型或行业扩展包。
- 不修改 Source、Negotiate、Purchase、Fulfill 的业务 Schema；仅在文档引用 Pay/Resolve 时修正明显错误。
- 不提交或推送 Git 变更，除非用户另行明确要求。
