# 支付与争议解决原语一致性修订技术方案 v2

## 一、审计结论

现有 50 个目标 Schema 均可解析，Draft 2020-12 元 Schema 与相对 `$ref` 基础检查已通过；主要风险位于跨实体业务语义和规范示例一致性。

### 1. Pay 高优先级问题

1. `confirm_output` 和 `term_output` 无条件要求 `PaymentConfirmation`，但状态机允许 `PROCESSING`、`FAILED`；异步或失败结果无法被当前输出 Schema 合法表达。
2. `refund_result` 仅在完成时要求 `PAYMENT_REFUNDED` 引用，但没有禁止 `processing`/`failed` 携带完成事件；状态机也可能在退款尚未完成时提前迁移。
3. 状态机使用 `payment_captured`、`payment_failed`，与标准 `PaymentEventType` 的 `PAYMENT_CAPTURED`、`PAYMENT_FAILED` 不一致。
4. `query_input.anyOf` 允许同时传 `payment_request_id` 与 `purchase_id`，与“二选一查询范围”语义不一致。
5. 通用 `Money` 允许负数，Pay 的扣付、确认、分账和退款字段没有进一步收紧，负支付和负退款可通过 Schema。
6. `RefundInstruction.scope_ref` 是可为空的开放对象，无法验证部分退款是否绑定付款阶段、订单、批次或商品。

### 2. Resolve 高优先级问题

1. `ResolutionOutcome` 允许 `continue`、`dismissed`、`escalated` 同时携带退款或取消指令，也未完整限制终止退款结果的可执行指令集合。
2. `CompensationResult.status=compensated` 时，子动作仍可为 `pending`/`failed`；`processing` 与 `failed` 也没有要求对应的子动作证据。
3. `resolve.compensate` 状态迁移无完成条件，渠道退款仍在处理中时也可能进入 `COMPENSATED`。
4. `DisputeRecord.status` 未与 `resolution_outcome`、`compensation_result`、`resolved_at` 建立条件约束，可产生“已补偿但没有补偿结果”等档案。
5. CompensationOrder、ResolutionOutcome 和 CompensateInput 分别重复承载处置数据，却缺少稳定标识和来源锚点，存在调用时篡改或漂移风险。
6. 责任比例只限制单项范围，比例合计为 1、主责层对应最大比例、补偿金额守恒与币种一致性仅有部分文字约束。
7. `mediate` 描述允许补充材料，但状态机没有 `MEDIATING → MEDIATING` 的合法重复提交路径。

### 3. 共享 Schema 与规范文档问题

1. HAI 同一 Schema 同时承载响应控制上下文与确认续跑附件，但字段未标注 `readOnly`/`writeOnly`，工具链无法稳定生成方向投影。
2. Pay/Resolve 规范示例仍把 `transaction_id`、`idempotency_key` 放在 `input`，把 `valid_next_actions` 放在 `output`，与统一 Action 信封冲突。
3. 文档示例仍使用 JSON number 表示金额，并存在 `type/trigger_type`、`fulfill_action/fulfillment_action`、`aggregate_status/status` 等字段和枚举不一致。
4. Resolve 示例的 LockPolicy、MediationResult、CompensationOrder、CompensateOutput 与迁移后的强类型 Schema 结构不一致。
5. Pay 状态图仍使用已废弃的 `pay.installment`，且未体现从已确认/已完成支付发起退款的路径。

## 二、修订设计

### 1. Pay 输出与状态闭环

- 为确认和付款阶段输出增加显式 `status`，按 `processing`、`confirmed`、`failed` 条件要求或禁止 `PaymentConfirmation`、PaymentEvent 和 PaymentProgress。
- PaymentEvent 使用标准事件枚举驱动状态迁移；资金变动事件必须具备正金额、支付请求、渠道流水和证据引用。
- 退款状态机仅在 `RefundResult.status=refunded` 时进入相应完成状态；`processing`/`failed` 保持原支付事实状态。
- 查询条件改为严格二选一；查询输出补齐稳定聚合标识和金额快照约束。
- 新增强类型 `refund_scope.json`，对部分退款范围做至少一个稳定资源引用的校验。

### 2. 金额约束

- 在 common/entities 中增加可复用的 `non_negative_money.json` 与 `positive_money.json`，继续复用 Money 的币种和小数字符串格式。
- 支付、确认、捕获、分账、退款、主张和补偿等实际金额使用正金额；累计已付、剩余、优惠等允许零的字段使用非负金额。
- 在原语约束中明确等式：金额分项合计、分账合计、累计支付守恒、补偿合计、责任覆盖及同一聚合币种一致。

### 3. Resolve 结果与补偿闭环

- 按 ResolutionResult 限制 instructions：继续、驳回、升级必须为空；部分补偿至少一条；终止退款至少包含 refund 与终止类指令。
- 按 CompensationResult 汇总状态限制子动作：processing 至少一个 pending；compensated 全部 completed 且有完成时间；failed 至少一个 failed。
- DisputeRecord 按状态要求对应的结果实体、完成时间和一致的内部状态。
- 为 CompensationOrder 增加稳定标识，为 CompensateInput 增加 ResolutionOutcome 来源锚点；运行时必须以权威档案为准，不信任调用方重复提交的金额和动作。
- 增加调解中补充材料自迁移；compensate 仅在全部动作完成时迁移到 COMPENSATED。

### 4. HAI 与文档同步

- HAI 响应字段标 `readOnly`，确认续跑附件标 `writeOnly`，保持单文件复用但可正确投影。
- 更新 Pay、Resolve Action 示例为统一信封：协议字段位于顶层，业务字段位于 input/output，valid_next_actions 位于响应顶层。
- 所有金额改为 decimal 字符串，字段名、枚举和嵌套对象严格匹配 Schema。
- 更新状态表和状态图中的废弃 Action 名称及退款/补偿完成条件。

## 三、文件影响

- 修改 Pay：`primitive.json` 与相关 entities，新增 `refund_scope.json`。
- 修改 Resolve：`primitive.json`、DisputeRecord、ResolutionOutcome、CompensationOrder/Result/Input、MediationResult 等。
- 修改 common：HAI，并新增正数/非负金额实体。
- 修改文档：Pay、Resolve 规范正文和示例；必要时同步两张状态图。
- 新增测试：以 Node 或 Python 的 Draft 2020-12 校验器执行引用解析和关键正反例，不引入生产依赖。

## 四、验证门禁

1. 目标 JSON 全部可解析，Draft 2020-12 元 Schema 全部通过。
2. 所有相对 `$ref` 和 JSON Pointer 均可解析，`$id` 唯一且为 HTTPS。
3. Action 引用、状态名、Action 名和标准 PaymentEvent 名称可静态关联。
4. 为确认/失败、退款处理中/完成、ResolutionOutcome 各结果、CompensationResult 各状态、DisputeRecord 关键状态和金额正负各提供正反例。
5. 规范文档中的 Pay/Resolve JSON 示例可被统一信封和对应 Action 输入/输出 Schema 校验。
6. 执行 `node --test docs/authoring/tests/*.test.mjs` 与 `git diff --check`。
7. 最终检查 diff 仅包含本任务文件，不覆盖用户已有无关改动。

## 五、兼容策略

- 对新迁移且尚未发布的强类型实体允许收紧明显无业务意义的组合。
- 不删除可合法扩展的 optional 字段；新增字段默认 optional，只有建立审计锚点或避免不可执行状态时才设为 required。
- 跨字段数值等式无法由 JSON Schema 精确表达的部分，保留明确的运行时 MUST 约束并配合测试样例说明。
