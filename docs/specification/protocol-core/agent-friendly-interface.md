# Agent 友好设计原则（Agent-Friendly Design Principles） {#s-19-agent-friendly-design-principles}

UTP 协议假设调用方 100% 是 AI Agent。所有原本由人类隐式承担的认知负荷——理解前置条件、推断下一步动作、处理异常恢复、协调多方——MUST 被显式编码进协议本身。本章规定协议层面的 Agent 友好**设计原则**与**合规等级（L4）要求**，用于指导传输层、P0 原语框架、各原语章节及人机协同章节的字段与行为设计。

**章节边界**：本章不定义具体的请求/响应字段、Action Object 结构、错误对象字段或传输信封字段；这些字段分别由[第 4 章 传输与通信](transport-communication.md)、[第 10 章 原语通用框架](primitive-framework.md)、各原语章节及[第 20 章 人机协同交互控制](human-agent-interaction.md)定义。本章只规定上述章节在面向 Agent 暴露接口时必须遵循的设计原则与判定标准。

接口设计遵循三条元原则：

- **契约最小化**：MUST 层只保留跨方语义必须一致的字段；提示性、策略性、UI 性字段 SHOULD 或 MAY 进入协议，不得一律提升为 MUST。
- **静态与动态分离**：会话内不变的信息在握手时下发并冻结，运行时通过引用携带；运行时才变化的信息在响应中内联。
- **核心闭合与扩展开放**：核心字段取值枚举封闭，领域差异走命名空间扩展，避免核心字段被无限追加。

## 自描述响应原则 {#s-19-1}

### 完整自描述原则 {#s-19-1-1}

每个 UTP 协议响应 MUST 包含足够的自描述信息，使 Agent 无需查阅外部文档即可理解当前状态、可用操作、风险边界和恢复路径。这是从传统 API 到 Agent 协议的关键范式转变：人类开发者可以读文档，Agent 只能解析结构化数据。

自描述信息由传输层、原语响应骨架与各原语业务输出共同承载：

- 响应信封层的会话标识、时间基准、状态版本、快照引用等由[第 4 章](transport-communication.md)定义。
- 动作标识、执行结果、当前原语状态及后续动作名称列表由[第 10 章 P0 响应骨架](primitive-framework.md#s-1023-action-definition-format)定义。
- 面向 Agent 的动作自然语言说明、输入提示、前置/后置条件、风险、确认、授权与恢复语义由各原语章节及本章设计原则共同约束。

协议实现方 MUST 保证：Agent 仅凭当前会话上下文、响应中的自描述字段和已协商的静态快照，即可决定下一步安全动作。

### 静态与动态分离原则 {#s-19-1-2}

会话内不变的信息（Mode、Topology、静态动作矩阵等）MUST 在握手时一次性下发并冻结；运行时响应 MUST 通过不可变引用携带，不得每次内联全量对象。运行时才变化的信息（当前状态、业务输出、可用动作实例、警告、错误恢复路径等）MUST 在响应中内联。

该分离原则的目的：

1. 减少重复传输，降低响应体积。
2. 保证会话各方对静态事实持有相同版本，便于一致性校验与争议取证。
3. 使 Agent 能够缓存静态上下文，只关注动态变化。

若响应中未内联运行时可用动作集合，则 MUST 提供可解析的静态动作矩阵引用，Agent MUST 能够基于当前状态、HAI 控制对象、会话快照和业务对象状态计算当前行动空间。

### 行动空间场景分层原则 {#s-19-1-3}

`valid_next_actions` 的必填强度 MUST 按响应场景分层，而非一律 MUST。分层原则如下：

| 场景 | 必填等级 | 原则说明 |
| --- | --- | --- |
| 存在活跃 HAI 挂起控制 | MUST | 只读白名单；控制动作 MUST 标注触发方不属于 Agent，防止越权 |
| 错误响应且 `recoverable=true` | MUST | 提供结构化恢复路径 |
| 状态一致性对账响应 | MUST | 状态不一致时显式指导修复路径 |
| 状态迁移刚发生 | SHOULD | 帮助 Agent 快速理解新状态下的行动空间 |
| 稳态运行时响应 | MAY | 静态可缓存，推荐通过引用推导 |

单个可执行动作的面向 Agent 语义（自然语言描述、执行入口、输入说明、前置/后置条件、风险、确认、授权、有效期、恢复提示等）由原语章节在 Action 操作说明块中定义；其运行时编码形态由 P0 原语框架及传输绑定共同决定。所有原语章节在暴露可执行动作时 MUST 遵循上述设计原则。

## 错误恢复原则 {#s-19-2}

### 可恢复错误必须携带结构化恢复路径 {#s-19-2-1}

UTP 的标准错误响应格式由 P0 原语通用框架定义。本章不重新定义基础 Error Object，而是规定错误响应面向 Agent 时必须携带的恢复语义：当错误 `recoverable=true` 时，MUST 提供可直接消费的结构化恢复路径，使 Agent 能够执行恢复动作，而非需要人类介入判断。

恢复路径的设计原则：

- 恢复动作 MUST 复用 P0 框架中 Action 的运行时表示，不得发明第二套动作描述语言。
- 每个恢复动作 SHOULD 内嵌面向 Agent 的决策提示，辅助 Agent 在多条路径中选择。
- 已知权威默认参数时，SHOULD 提供 `default_input`，避免 Agent 从先前上下文猜测参数。
- 已产生副作用且涉及 Saga 补偿的失败，MUST 通过审计引用暴露补偿链路，不得要求 Agent 推断补偿状态。

### 恢复动作必须可执行 {#s-19-2-2}

恢复动作 MUST 满足与普通可执行动作相同的自描述要求：具备标识、自然语言描述、执行入口、输入说明及必要的风险/确认声明。恢复动作不得是仅面向人类的文本说明或外部文档链接。

不可恢复错误 MUST 明确声明 `recoverable=false`，且不得提供虚假的恢复动作；Agent 收到此类错误后 MUST 停止盲重试，改为上报或进入人工接管流程。

## 幂等性与重试原则 {#s-19-3}

### 写操作必须幂等 {#s-19-3-1}

UTP 协议的所有写操作（所有会变更状态或产生副作用的 Action）MUST 支持幂等键（Idempotency Key）。幂等机制用于解决 Agent 在超时、中断、任务恢复或并发调用后"不知道上一次是否成功"的问题：Agent 可以用同一个幂等键安全重试同一业务意图，协议引擎 MUST 保证不重复产生下单、支付、退款、库存锁定等业务副作用。

幂等策略的声明位置、请求携带方式与响应回显方式由 P0 原语框架及传输层定义。实现方 MUST 保证：相同幂等键、相同业务意图的重复请求返回等价结果；相同幂等键但不同请求内容 MUST 作为冲突处理。

### 重试语义必须基于协议错误而非传输状态码 {#s-19-3-2}

重试决策 MUST 以 UTP 结构化错误语义为准，而不是以传输层状态码为准。协议只定义"是否可重试"、"是否必须使用相同幂等键"与"服务端节流提示"三项跨方契约；具体退避算法、最大次数和抖动策略属客户端 Agent 策略，不进协议核心。

HTTP 4xx/5xx 等状态码仅是具体传输绑定的映射结果，不能替代协议错误中的可重试声明。Agent MUST 根据 `error.retryable`、`error.recoverable`、`error.recovery_actions` 与 `error.retry_after` 做重试或恢复决策。

### 重试必须携带相同幂等键 {#s-19-3-3}

当 Agent 对写操作或有副作用 Action 进行重试时，MUST 携带与原请求相同的 `idempotency_key`。该要求适用于超时、暂时不可用、 rate limit 等可重试场景。

`IDEMPOTENCY_CONFLICT` 表示同一幂等键被用于不同请求内容，Agent MUST NOT 继续使用同一幂等键重试，必须刷新状态并重新建立业务意图。

## L4 Agent 友好度 {#s-19-4}

### L4 定义 {#s-19-4-1}

UTP 协议要求实现方达到 L4 Agent 友好度。这里的 L4 不是指 Agent 可以无条件自动执行所有交易动作，而是指协议响应提供足够的结构化语义，使 Agent 能够在权限、风险、确认、幂等和恢复规则约束下安全行动。各等级定义如下：

| 等级 | 名称 | 特征 | 典型代表 |
| --- | --- | --- | --- |
| L0 | 无结构化 | 纯 HTML/文本，无 API | 传统网页 |
| L1 | 结构化接口 | RESTful API + JSON，但语义靠文档 | OpenAPI 规范 |
| L2 | 自描述 | 响应包含状态和可用操作 | HATEOAS |
| L3 | 语义契约 | 接口携带前置/后置条件 | Protocol-style |
| L4 | Agent 自主 | 自描述响应 + Action 语义契约 + 风险/确认 + 幂等重试 + 结构化恢复路径 | UTP |

### L4 实现要求 {#s-19-4-2}

达到 L4 Agent 友好度，协议实现方 MUST 满足以下要求：

| 要求编号 | 要求描述 | 必要性 |
| --- | --- | --- |
| L4-01 | 状态型响应 MUST 携带自描述响应信封；关键节点响应（活跃 HAI 挂起 / 错误 / 对账）MUST 内联 `valid_next_actions`；状态迁移响应 SHOULD 内联；稳态响应 MAY 用可解析引用替代。响应信封字段定义见第 4 章。 | 必须 |
| L4-02 | 错误响应 MUST 使用 P0 标准错误格式；当 `error.recoverable=true` 时，MUST 包含可执行的 `recovery_actions`。 | 必须 |
| L4-03 | 每个可执行 Action 的运行时表示 MUST 包含动作标识、自然语言描述与执行入口；前置/后置条件 SHOULD 存在。具体字段定义见第 10 章及各原语章节。 | 必须 |
| L4-04 | 每个写操作或有副作用 Action MUST 声明幂等策略，执行请求 MUST 携带 `idempotency_key`。 | 必须 |
| L4-05 | 涉及 Saga 或已产生副作用的失败 MUST 暴露补偿状态；若已执行补偿，MUST 通过审计引用暴露链路。 | 必须 |
| L4-06 | 涉及资金、合同、库存、履约、合规或不可逆后果的 Action MUST 携带风险声明；需要用户或审批人确认时 MUST 携带面向人类的确认摘要。 | 必须 |
| L4-07 | 响应 SHOULD 包含协议级 `warnings` 预告潜在问题。 | 建议 |
| L4-08 | 每个恢复动作 SHOULD 内嵌面向 Agent 的决策提示，辅助其在多条恢复路径中选择。 | 建议 |
| L4-09 | 协议实现方 MAY 提供操作推荐、排序或决策提示；推荐信息不得覆盖风险、确认、授权和幂等约束。 | 可选 |

### Agent 决策支持模式 {#s-19-4-3}

UTP 协议通过以下机制支持 Agent 自主决策：

**前置条件检查**：Agent 在执行任何动作前 SHOULD 校验其前置条件。协议引擎在接收到请求后 MUST 做权威校验；若前置条件不满足，MUST 返回结构化错误并在可恢复时提供恢复路径。

**后果预判**：可执行动作 SHOULD 包含后置条件摘要；涉及实质风险的 Action MUST 通过风险声明与确认摘要表达后果和人工确认要求。

**决策提示**：实现方 MAY 提供基于上下文的决策提示，但提示信息不得覆盖风险、确认、权限和幂等约束，也不得被 Agent 当作权威业务事实。

### Profile 中的友好度声明 {#s-19-4-4}

本规范不在 UTP Profile 中定义友好度声明字段。L4 的各项"必须"要求均为本章及各引用章节的规范性要求，合规的 UTP 实现天然满足 L4，无需额外声明；实现方的能力边界通过 Profile 既有的能力声明与 HAI 会话能力声明表达。L0–L3 等级仅作为与现有行业接口形态对照的非规范性参照。
