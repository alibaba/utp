待优化项（交互对比）

4. primitive / extension 命名正则未覆盖下划线与多级扩展 待优化

profile.json 与 negotiation_result.json 中用于校验 primitive 名称的正则仅允许 [a-z0-9-]，但项目已使用 utp.source_cart 这类带下划线的扩展名，未来还可能出现多级扩展（如 utp.xxx.yyy）。

当前正则
"^utp\\.[a-z0-9-]+$"
建议正则
"^utp\\.[a-z0-9_-]+(?:\\.[a-z0-9_-]+)*$"
5. extension 定义字段不一致 待优化

profile.json 与 negotiation_result.json 都定义了 extension，但字段命名与必填项不同，可能导致解析代码重复或数据转换错误。

profile.json 当前定义
"extension": {
  "properties": {
    "name": { "type": "string", "minLength": 1 },
    "version": { "$ref": "#/$defs/version" },
    "schema": { "type": "string", "format": "uri" }
  },
  "required": ["name", "version", "schema"]
}
建议统一为
"extension": {
  "properties": {
    "name": { "type": "string", "minLength": 1 },
    "version": { "$ref": "#/$defs/version" },
    "schema": { "type": "string", "format": "uri" },
    "spec": { "type": "string", "format": "uri" }
  },
  "required": ["name", "version", "schema"]
}
6. action_response.json 缺少 execution_result 必填约束 待优化

action_response.json 的 required 只有 action 与 session_id，但 execution_result 是状态机分支判断的核心字段，遗漏会导致响应语义不完整。

当前 required
"required": [
  "action",
  "session_id"
]
建议 required
"required": [
  "action",
  "session_id",
  "execution_result"
]
7. 全局状态机请求 schema 使用非标准关键字 utp_request 待优化

state_notify_request.json 与 state_query_request.json 中使用了 utp_request 字段，它不是 JSON Schema 2020-12 关键字。虽然不会导致校验失败，但可能被自定义代码生成器误解。

当前写法
"action_response": {
  "$ref": "...",
  "utp_request": "required"
},
"state_views": {
  ...
  "utp_request": "required"
}
建议写法
"action_response": {
  "$ref": "...",
  "description": "action_response 为必填字段。"
},
"state_views": {
  ...
  "description": "state_views 为必填字段。"
}

其他观察

  • action_request.json 与 action_response.json 的 HAI 字段不一致：请求信封中 hai 内联定义，响应信封引用 hai.json。若语义相同，建议统一引用 hai.json。
  • money.json 金额正则可接受前导零：如 "001.00" 可通过校验。业务若不允许前导零，可收紧正则。
  • 所有 $ref 引用已解析通过，无死链、无重复 $id、无无效正则。
